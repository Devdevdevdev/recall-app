## Criterion classes and safe comparison contract

Across every class: require a CPSC source-bound address and current source revision, a human-reviewed mandatory/descriptive decision, exact product context, a typed owned-product field with known capture provenance, and `needs_review` whenever required evidence is missing or unparsable. A match on a code must never erase another mandatory condition. A contradiction can reject only when the reviewer established that the criterion exhaustively describes the affected set. Page prose may propose candidates but cannot authorize them.

| Class                               | Evidence, normalization, comparison, owned field                                                                                                                                                                                | Decision for 16.9                                                                                                                                                                                                     |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_exact`                       | Explicit model label in API prose/page or structured field; preserve punctuation and leading zeroes, normalize only case/spacing under a recorded rule; exact equality to `modelNumber` with product/brand context.             | **Recommend reviewed support** for unqualified, exhaustive model statements.                                                                                                                                          |
| `model_set`                         | Explicit complete list/table with row identity; de-duplicate exact models, preserve row links; membership of `modelNumber`. “Including models” can support positive matches to listed models but cannot reject unlisted models. | **Recommend reviewed support** with completeness flag.                                                                                                                                                                |
| `serial_exact`                      | Textual serial value explicitly affected; case/space normalization only if source format allows; exact `serialNumber`.                                                                                                          | **Conditional**; none in cohort.                                                                                                                                                                                      |
| `serial_prefix`                     | Source explicitly says “begins with” and gives prefix; anchored prefix against `serialNumber`, preserving width and alphabet.                                                                                                   | **Conditional**; do not infer from masked examples.                                                                                                                                                                   |

## Candidate extraction, human approval, and source addressing

**Stage A — candidate extraction:** a deterministic parser may emit `unreviewed` proposals with source address, text/table-cell fingerprint, type, value or range, required/descriptive/ambiguous suggestion, grouping, completeness, and parse confidence. Page tables need a reviewed authoritative-page ingestion layer that stores the CPSC URL, retrieval time, normalized section/table cells, page revision, and audit snapshot. Keep HTML and API revisions separate. AI, if ever used, may only propose the same `unreviewed` structure; no paid inference is needed here.

**Stage B — human approval:** a person opens the official URL and the exact addressed field/section/table row, sees the raw phrase and normalized candidate, all required conjunctions and alternatives, payload/page hashes, source revision, and any unavailable values. The person explicitly accepts or rejects each proposal and the complete criterion group. Capture reviewer identity/time, rationale, review status, completeness assertion, and immutable approved criterion version. Codex and any future model are candidate tools, **not human reviewers**. Only `reviewed` and current-source-valid criteria may become production-v2 eligible; this phase created none.

Proposed stable address, for example:

`cpsc:<source UUID>:<external ID>:<recall number>:<canonical URL path>:api/<field path or page/Recall Details/Description/table[caption-or-header-hash]/row[key]/cell[header]>:<payload-or-page-section SHA-256>:<normalized evidence SHA-256>`

Store each component separately. For API arrays include product/scope index **and** product-row content fingerprint; for page tables include header fingerprint and stable row key such as model/item number, plus neighboring label context. A character offset may aid display but is never the sole address. Normalize whitespace/Unicode deliberately, keep original short evidence and its digest, and disallow addresses to image-only content. The source UUID and external ID remain in the address, but canonical URL path plus recall number also detect the observed ID drift and duplicate pages.

On every source refresh, recompute canonical payload hash and relevant page-section fingerprints. Any changed payload hash first makes the approval **stale pending semantic revalidation**; a changed official URL identity, missing/moved section or table row, changed normalized criterion, changed list completeness, changed conjunction/alternative semantics, or changed evidence fingerprint invalidates it outright. Never silently carry approval across a source revision or a new scope ID. Ignore only a demonstrably irrelevant page chrome change after re-fetching and comparing the addressed normalized evidence, and record that revalidation. If the current API ID maps to an already stored page/recall number, hold both identities for deduplication review; neither may inherit the other's approval. Stale/ambiguous criteria expose `needs_review` and cannot create new eligibility. Existing alert history would require the separate correction path, not silent deletion.

## Phase 16.9 recommendation and stop gate

1. Resolve the observed CPSC `RecallID` drift and three duplicate stored official pages in ingestion identity logic **before** building an approval route; determine whether the authority changed IDs or the current `(source_id, external_id)` strategy permits duplicate recall-number/page identities. Do not rewrite historical rows in this audit.
2. Build a read-only, versioned CPSC page snapshot/parser prototype for Recall Details text and HTML tables, with section/row addresses and explicit API/page revision comparison. Validate all 27 distinct pages and the four regression examples. This is necessary for the six rows with material page-only tables; do not deploy page scraping from this gate.
3. Define an `unreviewed → reviewed/rejected → stale` review ledger and a human UI that shows whole criterion groups, not just isolated values. Add source-hash and official-page evidence binding, group completeness, and source revision invalidation before any production binding. Keep the matcher selector and consumer reads unchanged.
4. Start only with reviewed exact model/model-set and exact/set date-code proposals where the source explicitly states exhaustive eligibility, and add conjunction/alternative representation before cases such as Thermos, Orb, Melissa & Doug, AGA, and Char-Broil. Defer wildcard serial/VIN ranges, unknown serial subsets, untyped codes, and undefined feature conditions. No criterion is approved by this report.

Deterministic candidate extraction is sufficient for labeled exact models, item/SKU lists, literal date codes, explicit date boundaries, and well-formed HTML tables **as proposals**. It is not sufficient to approve whether a color is mandatory, whether “including” is exhaustive, whether a serial wildcard has valid ordering, or whether an unlabeled sticker code is an eligibility key. Future AI could help propose those difficult interpretations, but independent human approval remains mandatory and automatic confirmation never consumes AI proposals.
